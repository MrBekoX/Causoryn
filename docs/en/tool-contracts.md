## Tool Profiles (`--tool-profile` & `CAUSORYN_TOOL_PROFILE`)

Causoryn registers only the tools of the active profile in `tools/list`. The default `core` profile keeps the host model's context small: `tests/mcp-tool-surface-budget.test.ts` asserts that the core `tools/list` payload stays at or below 15,000 characters and that the `causoryn_export_documentation` entry stays at or below 1,800 characters.

| Profile | Registered tools | Notes |
|---|---|---|
| `core` *(default)* | **11** (`CORE_TOOL_NAMES`) | Consolidated everyday surface. Lean wire schemas for `causoryn_export_documentation`, `causoryn_preflight_change` and `causoryn_verify_change` (same server-side validation as the full schemas). |
| `wiki` | **18** (11 core + 7 `WIKI_TOOL_NAMES`) | Adds the Living Wiki tools. |
| `history` | **13** (11 core + 2 `HISTORY_TOOL_NAMES`) | Adds `causoryn_compare_architecture` and `causoryn_architecture_timeline`. |
| `wiki,history` | **20** | Profiles combine with commas; duplicates are ignored. |
| `full` | **32** (29 `TOOL_NAMES` + `causoryn_status`, `causoryn_trace`, `causoryn_contracts`) | Backward-compatible catalog. `full` includes everything, so `full,wiki` equals `full`. Superseded legacy tools are marked deprecated (see below). Full-profile input schemas are used for export, preflight and verify. |

**Selection order** (`runtime-cli.ts` `resolveMcpServerSettings` / `resolveEffectiveToolProfile`): `--tool-profile <list>` > `CAUSORYN_TOOL_PROFILE` > `CAUSORYN_CONFIG.toolProfile` > `core`, the same for `causoryn mcp` and the bare bundle entry (`dist/mcp-server.mjs`). Every supplied value is validated, including one that a higher-precedence source overrides; unknown or empty profile names are rejected at startup with a usage error (exit code `2`). When the server is embedded programmatically, `createCausorynMcpServer(context, { toolProfile })` takes the option first, then the optional `toolProfile` field of `CAUSORYN_CONFIG`, then `core`; invalid names throw.

**Deprecation in `full`:** for every name in `DEPRECATED_TOOL_REPLACEMENTS`, the tool description ends with `(Deprecated: use <replacement>)`, and every non-error envelope gets the warning `[Deprecated in favor of <replacement>] Legacy tool <name> will be removed in a future release.` The data payload is unchanged. See [Legacy Tool Replacements](#legacy-tool-replacements).

## Standard Envelope & Per-Language Coverage

Every tool returns the strict 10-field `EnvelopeSchema` (`packages/mcp-server/src/envelope.ts`, `z.strictObject`):

1. `schemaVersion` — always `"2.0"` (`SCHEMA_VERSION`).
2. `requestId` — the MCP request ID as a string.
3. `workspaceId` — `string | null`.
4. `snapshotId` — `string | null`: the `GraphSnapshot` ID for graph tools, the served `WikiSnapshot` ID for wiki tools, `null` for tools that do not read a snapshot (for example a refresh request or a capabilities-only call).
5. `status` — `"ok" | "partial" | "error"`. `partial` means the result is usable but incomplete (partial snapshot, unresolved chain, indexing still running).
6. `coverage` — `{ tier, resolvedEdges, unresolvedEdges, totalEdges, coverageRatio, byLanguage? } | null`. `tier` is `L0`–`L4`.
   - **`coverage.byLanguage`** is an optional record keyed by language (sorted keys) with `{ tier (L0|L1|L2), files, verifiedEdges, heuristicEdges, unresolvedEdges, coverageRatio }`, so strong TypeScript coverage cannot hide an `L0` fallback in C#, Python, Go or Rust.
7. `warnings` — `string[]` (stale snapshot, clamped limits, deprecation, trust warnings, degraded legs).
8. `data` — the tool payload; the candidate list on `AMBIGUOUS_SYMBOL`; the indexing-in-progress object (below); or `null` on other errors.
9. `nextCursor` — `string | null` (opaque pagination cursor).
10. `error` — `null` when `status` is `ok` or `partial`; `{ code, message, retryable, userAction }` when `status` is `error`.

Domain, policy and authorization errors travel inside `envelope.error` with MCP `isError: false`; they are never protocol crashes. Inputs that fail the wire schema are rejected by the MCP SDK with a protocol-level `isError: true`; inputs that pass the schema but violate semantic rules return an envelope `INVALID_ARGUMENT`. `INTERNAL_ERROR` is the catch-all for unexpected failures on every tool: the raw message is logged to `stderr` only, and the client receives a generic message that includes the `requestId`.

`stdout` carries only MCP JSON-RPC frames; operational logs go to `stderr` with a `[causoryn]` prefix. Every tool declares MCP `annotations` with `destructiveHint: false` and `openWorldHint: false`; `readOnlyHint` is listed per tool below.

For the same published snapshot and equivalent inputs, analysis data is ordered deterministically. `requestId`, job progress, timestamps and `stale` reflect runtime state.

### Indexing, Freshness & Progress

- **Bounded wait:** before running any tool except `causoryn_status`, `causoryn_get_capabilities`, `causoryn_index_status` and `causoryn_refresh_index`, the server waits up to `CAUSORYN_INDEX_WAIT_MS` (default `15000`; `0` = do not wait) for the first index. Indexing runs in a `worker_threads` worker with an in-process async fallback, so the MCP event loop stays responsive.
- **Indexing-in-progress envelope:** if a graph tool would fail with `INDEX_NOT_READY` while an index job is running, the server returns `status: "partial"`, `snapshotId: null` and `data: { indexing: true, status: "indexing", jobId, progress: { phase, completed, total: 100 }, retryAfterMs: 3000 }` plus a warning naming the job. Wiki tools are excluded from this conversion and return `INDEX_NOT_READY` as usual.
- **Progress notifications:** clients that send `_meta.progressToken` receive MCP `notifications/progress` while the call waits for the first index (best effort; a closed transport never fails the call).
- **Stale snapshot:** while a re-index is running, non-wiki responses that carry a snapshot get the warning `stale=true: background re-indexing is currently running; serving latest published snapshot`. Readers always see the latest published snapshot, never a half-built one.

**Core input-schema note:** in the `core` profile, `causoryn_export_documentation` advertises a lean schema (`view` is a string, `annotations` is a generic object, `options.maxModules` accepts 1–200 on the wire), and `causoryn_verify_change` advertises `observedTestRun` as a generic object. **Input limits:** every string and array in the tool input schemas has a finite maximum (IDs and cursors 512 characters, Git refs 200, paths 4096, queries and names 1024, intents and tasks 8192, lists 200 items; enum arrays by enum size). `causoryn_architecture_timeline` accepts at most 100 `refs`. Onboarding limits are clamped to their ceilings (`entryPointLimit` 100, `topModuleCount` 100, `maxLearningSteps` 500, `maxCriticalFlows` 50) with an `onboarding/limit-clamped` warning. Identical queued index refreshes are merged into the waiting job (with a warning), and at most 16 refreshes can wait (`LIMIT_EXCEEDED` beyond that).

### Architecture Export Details

- **Views and default file names:** `architecture` is the default view for `json`, `markdown`, `mermaid` and `html` (`causoryn-architecture.json`, `.md`, `.mmd`, `.html`). `interactive` is HTML only and defaults to `causoryn-architecture-interactive.html` (`EXPORT_INTERACTIVE_HTML_FILE_NAME`), so it never overwrites the zero-JS file. `view: "full"` is the unfiltered raw dump and cannot be combined with `options` or `annotations`; its Markdown form escapes every table cell and snapshot meta line like the architecture brief (link, image, HTML, code-span, `~` and table syntax backslash-escaped, line breaks collapsed, control characters replaced with U+FFFD) and defangs bare autolinks (`https\://`, `www\.`, `user\@host`, also inside `mailto:` / `xmpp:`), so repository text does not turn into clickable links. `format: "snapshot"` (view omitted or `full`) writes the canonical `architecture-snapshot.json` content set used by the comparison tools. `view: "wiki"` is rejected with `INVALID_ARGUMENT`; wiki pages belong to the wiki tools.
- **Projection options** (`architecture` and `interactive` only): `maxModules` 2–100 (default 32), `pathPrefix` (relative POSIX prefix, ≤ 260 chars, no `..` or NUL), `includeTests` (default `true`). `architectureSummary.moduleIds` returns the exact module IDs to reference in `annotations` for the same projection.
- **Annotations:** optional host-written `title`, `architectureStyle`, `executiveSummary`, `domains`, `moduleNotes`, `flows`, `guidedTour`, `decisions`, `risks`. Every `moduleId`, `nodeId`, `evidenceId` and `keyFiles` path is checked against the projection and snapshot; up to 25 schema and reference errors are collected in one `INVALID_ARGUMENT` message (`MAX_VALIDATION_ERRORS`). Field budgets are listed in the [Prompting & Architecture Portals Guide](prompting-and-architecture-portals.md); the `architecture-blueprint` skill (`skills/architecture-blueprint/SKILL.md`) carries the full template.
- **Offline security:** the zero-JS HTML uses `default-src 'none'; style-src 'unsafe-inline'; base-uri 'none'; form-action 'none'`. The interactive HTML uses a hash-pinned script policy `script-src 'sha256-<hash>'` with no `'unsafe-inline'` scripts, no CDN, no network calls.
- **Atomic write:** content goes to a temp file the export creates itself next to the target (random name `.<file>.<hex>.tmp`, `flag: "wx"`; mode `0666` narrowed by the umask, which the published file keeps after the rename) and is renamed onto the target. The target directory's identity (`dev`, `ino`; no link) is bound from authorization to the rename, and before any content is written and again before the rename the entry at the temp path must be the file the export's descriptor refers to; otherwise the publication is refused with `PATH_DENIED` and nothing is published. Only that temp file is ever removed: a pre-existing `<target>.tmp` is left alone. The target must pass `OutputAccessPolicy` for `output.allowedOutputDirs` (`EXPORT_NOT_ALLOWED` when outside the list or when the list is empty; `PATH_DENIED` for separators, traversal, NUL bytes or symlink escapes in `fileName`).
- **Determinism:** the same snapshot, format, view, effective options and validated annotations produce byte-identical files (`packages/graph/test/architecture-export.test.ts`).

### Error Code Methodology Note

The per-tool "typical error codes" columns come from static reading of the `services*.ts` handlers and their mapping helpers (`graphErrorToToolError`, `wikiErrorToToolError`, `contractErrorToToolError`, `preflightErrorToToolError`, `verificationErrorToToolError`, `indexingErrorToToolError`). Because the shared helpers map whole error families, a column can list a code that a specific tool rarely or never produces. For consolidated core tools the column is the union of the legacy tools they cover. The exact behavior is pinned by the negative unit and integration tests (see [Implementation Status](implementation-status.md)). `INTERNAL_ERROR` applies to every tool and is not repeated in the columns.

### 4. Pagination & Server Limits

- **Opaque cursors** (`packages/mcp-server/src/cursor.ts`): base64url-encoded `{ "v": 1, "o": <offset> }`. Undecodable, tampered or old-format cursors return `INVALID_ARGUMENT`. On the last page `envelope.nextCursor` is `null`.
- **Configured limits** (reported in `capabilities.limits`; set in `CAUSORYN_CONFIG`): `index.maxFiles` 50,000, `maxFileBytes` 2,000,000, `results.maxNodes` 250, `results.maxSymbols` 100, `results.maxDepth` 3, `results.maxPaths` 50.
- **Tool-level ceilings:** contract tools accept at most 25 pairs, spec paths or anchor files per list; wiki pages default to 50 and cap at 200; `maxProximityDepth` caps at 4; impact analysis caps at depth 8, 20 paths, 250 nodes; the timeline caps at 60 revisions and a 500-commit walk; the preflight manifest store keeps 200 entries.

| `causoryn_compare_architecture` / `causoryn_architecture_timeline` *(history/full)* | `false` | Only the commit-analysis cache `<data root>/history/<commitSha>-<key>.json` (the directory of `storage.dataDbPath`; owner-only, atomic write), and only when the data root is outside every workspace root. On Windows the cache is written only when its real path lies inside the user's profile or `%LOCALAPPDATA%` with no link or junction below them. Without a data root, or with an untrusted cache directory, nothing is written. |
| `causoryn_preflight_change` / `causoryn_verify_change` | `true` | Zero bytes to disk. `preflight_change` keeps its manifest in the in-process `PreflightManifestStore` (FIFO, 200 entries) so `verify_change` and `include: ["test-plan"]` can resolve the `preflightId`; `verify_change` indexes the working tree into a scratch in-memory repository. |
| All other tools | `true` | Read-only. |

Indexing itself (any refresh or the initial index) may also build the Rust worker on first use from a staged copy of its crate in the external build cache (default `~/.causoryn/cache/rust-worker-target`, override `CAUSORYN_RUST_TARGET_DIR`) and record its SHA-256 pin there — never inside the workspace (a cache directory inside the workspace is refused). With `--auto-data-dir` all hosts that open the same workspace share one `graph.sqlite`; the `build_leases` table (heartbeat leases, default TTL 120 s, PID liveness on the same host) prevents two concurrent publishers.

## Honest Limits

- **No test execution:** `causoryn_verify_change`, `causoryn_preflight_change` (test-plan section) and `causoryn_derive_test_plan` never run tests. Test status is `not_run` unless the host passes `observedTestRun`; host data is always stored as `state: "host_asserted"` with `engineVerified: false`, never as engine-verified.
- **`no_findings` is not a correctness guarantee:** every verification report carries `disclaimers`. Requesting the `contracts` check in `causoryn_verify_change` currently yields `not_evaluated` (verdict `inconclusive`, with a warning), because that tool has no before/after spec pairs; use `causoryn_contracts` for contract checks.
- **Preflight manifests live in memory:** they are lost when the server restarts. An unknown or evicted `preflightId` returns `INVALID_ARGUMENT`; pass `baseSnapshot` instead.
- **History tools prefer trusted sources:** `causoryn_compare_architecture` and `causoryn_architecture_timeline` use the published local index for a ref only when it provably matches that ref (every indexed file still has its indexed hash, its git blob ID equals the commit tree entry, and every other path of the commit is excluded by the workspace rules), and for `working-tree`. Any other commit is analyzed from its git objects: the tree is listed and the blobs are read with the hardened read-only git calls (no checkout, nothing written into the workspace), only the paths the workspace rules would index are read (symlinks, submodules, ignored or secret paths such as `.env*` / `*.pem`, files above `maxFileBytes` and the committed snapshot file are never read; a file the policy refuses only because of the working tree, such as a link on its path, is counted as not analyzed in the point's note; more than `index.maxFiles` files fails that point), and a scratch in-memory index analyzes them with the same analyzers, so commit points have the same symbol granularity as index points. Approximation: source files come from the commit, while project and build inputs outside the inventory (`.csproj` / `Directory.Build.props` for the C# project model, installed `node_modules` / NuGet packages) and the workspace rules come from the current working tree and configuration; content hashes use the committed bytes, so line-ending conversion (`core.autocrlf`) shows as changed files against the working tree. Each analyzed point is noted in `warnings` (`'<ref>' (commit <sha12>) was analyzed from its git objects (…)`, plus `served from the history cache`). With a data root (`--auto-data-dir` or `storage.dataDbPath`) results are cached in `<data root>/history/<commitSha>-<key>.json` (owner-only, atomic write; the key covers the Causoryn version, the analyzer fingerprint schema, the workspace rules and the analyzed workspace (id and canonical root); corrupt entries are removed and re-analyzed; an analysis that ran without an available language worker is cached with that worker named in its note and is analyzed again once an index build runs that worker, when the budget allows; until then the cached result is used). Fresh analyses are budgeted per call (compare 2, timeline 4; `CAUSORYN_HISTORY_MAX_ANALYSES=<positive integer>` overrides both; an invalid value is ignored); cache hits are free and the same commit named twice is analyzed once. Fresh analyses run in a worker thread (the index worker's inventory-analysis mode in `dist/index-worker.mjs`; up to 2 idle workers are kept for 30 s and reused), so the MCP thread keeps answering; the worker's heap is capped at 256 MiB plus 24 MiB per started MiB of `CAUSORYN_HISTORY_MAX_COMMIT_BYTES` (1024 MiB by default; at most half of the machine's memory and 8192 MiB, never below 256 MiB) and the worker is terminated at the analysis or call deadline. Fresh analyses also run within resource limits (defaults; each `CAUSORYN_HISTORY_*` variable takes a positive integer, `CAUSORYN_HISTORY_BUSY_WAIT_MS` also `0`; an invalid value is logged and ignored): at most `CAUSORYN_HISTORY_MAX_COMMIT_BYTES` (32 MiB) of source text per commit and `CAUSORYN_HISTORY_MAX_REQUEST_BYTES` (64 MiB) per call, a wall-clock deadline of `CAUSORYN_HISTORY_MAX_ANALYSIS_MS` (120000) per analysis and `CAUSORYN_HISTORY_MAX_REQUEST_MS` (300000) per call (checked between tree entries and blob reads and at every progress message of the worker, enforced by a timer that terminates the worker, and passed to every git process as its timeout), and at most `CAUSORYN_HISTORY_MAX_CONCURRENT` (1) fresh analyses running at once in the server process; a call waits in FIFO order up to `CAUSORYN_HISTORY_BUSY_WAIT_MS` (30000) for a free slot, and when 16 calls are already waiting it is busy at once. A limit that is hit leaves the point unanalyzed with the reason `<code>: <detail>` (`commit-byte-budget-exceeded`, `request-byte-budget-exceeded`, `analysis-deadline-exceeded`, `request-deadline-exceeded`, `analysis-busy`; a worker that runs out of memory: `analysis-memory-exceeded`; one that crashes or exits: `analysis-worker-failed`; an aborted worker is asked to stop its sidecars, terminated after 1 s, and its remaining sidecar processes are killed; the call returns within about 2 s while the slot stays taken until the thread has exited, at most 60 s) and a warning; other calls keep being answered. The cache is trusted only as a real directory directly inside the data directory that, on POSIX, is owned by the server's user and not writable by group or others; an entry must pass the same owner and mode checks on its path and on the opened descriptor (same file) and must name the analyzed workspace, otherwise it is ignored with a log line, never served. Windows ACLs cannot be inspected, so on Windows the cache is trusted only when its real path lies inside the user's profile or `%LOCALAPPDATA%` (the default `~/.causoryn` does) and no path component below them is a link or junction; any other data root (for example a `--data-dir` in a new folder at a drive root) gets fresh analyses and no cache writes. The directory's identity is checked again right before each temporary-file create, rename and unlink. After each store, entries beyond `CAUSORYN_HISTORY_CACHE_MAX_ENTRIES` (256) or `CAUSORYN_HISTORY_CACHE_MAX_BYTES` (1 GiB) are evicted oldest first, and temporary files of writes that never finished (older than an hour) are removed. A point that is not analyzed (budget used up, limit hit, analysis failed) falls back to the `.causoryn/architecture-snapshot.json` committed at the ref (create it with `format: "snapshot"` and commit it), which a pull request can change, so such points carry `snapshot-loaded-from-committed-git-blob`; without that file the point stays `unanalyzed` with `analysis-budget-exceeded`, the limit's code, or `commit-analysis-failed`.
- **Rules source differs:** `causoryn_check_architecture` reads rules from the working tree; `causoryn_verify_change` reads them from the trusted `baseRef` and warns when it has to fall back to the working tree.
- **Warm start refresh:** when a published snapshot already exists in the SQLite store, the server serves it immediately and queues one background incremental refresh to pick up files changed while it was not running. Later edits are not watched; run `causoryn_status` with `action: "refresh"` after code changes.
- **No file-watcher tool:** there is no MCP tool that watches files; re-indexing is always requested explicitly.
- **Reserved fields are rejected, not ignored:** `scope` (refresh, wiki build, wiki search), `policyId`, `focus`, `granularity`, `candidateScope` and the extra wiki search filters return `INVALID_ARGUMENT`; `level: "L4"` is rejected by `causoryn_map_system`.
- **Contract projection is budgeted:** besides the parser limits (1 MiB, depth 64, 250,000 nodes, YAML alias quotas), each OpenAPI or AsyncAPI document has a deterministic projection work budget (`MAX_PROJECTION_WORK_UNITS`, 1,000,000 units; emitted text counts 1 unit per full 64 characters). A spec whose routes, channels or shared `$ref` schemas fan out beyond it fails with `LIMIT_EXCEEDED` (`contracts/limit-exceeded`, counts only in the message). Before that, the work of converting a YAML or JSON spec (the `yaml` library's `toJS`, which alias and anchor patterns can make expensive for a small file) is estimated from the document tree and bounded by `MAX_SPEC_CONVERSION_WORK` (30,000,000 units); a spec over it fails with the same `contracts/limit-exceeded`, in contract parsing and in the discovery sniff. Ordinary specs use a small fraction of both budgets and project exactly as before.
- **Search legs degrade visibly:** the agent-context `fts` leg needs a SQLite store; the wiki search graph-proximity leg is reported in `skippedRankLegs`.

## Output Schema Profile & Validation

- **Wire profile:** `--output-schema <omit|full>` (alias `--output-schema-profile`) > `CAUSORYN_MCP_OUTPUT_SCHEMA_PROFILE` > `omit` (`runtime-cli.ts` `resolveEffectiveOutputSchemaProfile`). `createCausorynMcpServer` also defaults to `omit` when embedded. Invalid values are rejected at startup.
- **`omit`** leaves `outputSchema` out of `tools/list` to save host context; the server still parses every envelope with the tool's output schema before returning (`registration.outputSchema.parse(envelope)` in `server.ts`). A response that fails this check is replaced by an `INTERNAL_ERROR` envelope.
- **`full`** publishes each tool's JSON Schema `outputSchema`; the MCP SDK then validates `structuredContent` against it on every call.
- Every result carries the envelope both as `structuredContent` and as JSON text in `content[0]`.

## Startup, Root Binding & Data Directory (Summary)

The packaged server (`causoryn mcp`, built from `packages/mcp-server/src/cli-stdio.ts`) binds a workspace root from `--root`, `CAUSORYN_CONFIG.allowRoots`, a safe current directory (`--allow-cwd`), or the first safe MCP `roots/list` entry. Unsafe candidates (filesystem roots, `$HOME` and its ancestors, Causoryn data and plugin directories, sensitive and system directories, UNC/device paths) are rejected. `--auto-data-dir` provisions `<base>/workspaces/<slug>-<hash12>/graph.sqlite` and `exports/` outside the workspace (base: `--data-dir` > `~/.causoryn` for every host; `ZCODE_PLUGIN_DATA` only as a fallback when `~/.causoryn` is unusable); none of these directories may be a link, and on POSIX they must be owned by the server's user (base and `workspaces` not writable by group or others, the workspace and `exports` directories `0700`). Without any root the server starts with `allowRoots: []` and workspace tools return `WORKSPACE_NOT_AUTHORIZED`. A graph or wiki database records the canonical root of `allowRoots[0]` for its `workspaceId`; a database recorded for another root under the same `workspaceId` stops startup with `CausorynConfigError` instead of being served. Full details: [CLI & Configuration](cli-and-configuration.md).
