# Security Policy

## Supported Versions

Causoryn is currently **pre-1.0 (`0.3.x`)**. Security fixes are provided for the latest `0.3.x` release line:

| Version | Supported |
|---|---|
| `0.3.x` | Yes |
| `0.2.x` | No (upgrade to `0.3.x`; see the migration notes in `CHANGELOG.md`) |
| `< 0.2.0` (`0.1.0` snapshot) | No |

## Reporting a Vulnerability

**Please do not report security vulnerabilities through public GitHub issues, pull requests, or discussions.**

Instead, use **GitHub Private Vulnerability Reporting**:

- Open a private security advisory at: <https://github.com/MrBekoX/Causoryn/security/advisories/new>

Include as much of the following as possible:

- Affected version (`causoryn --version` or commit SHA) and host client (Antigravity, Claude Code, Codex, ZCode, or standalone stdio)
- Operating system, architecture, and Node.js / sidecar toolchain versions
- Minimal reproduction steps or proof-of-concept input
- Expected security boundary vs. observed behavior

### Response SLA

- **Acknowledgment:** within **72 hours**
- **Initial triage and severity assessment:** within **7 calendar days**
- **Remediation & coordinated disclosure:** target **30 days** for Critical/High findings and up to **90 days** for Medium/Low findings, coordinated with the reporter before public disclosure

## Threat Model & Security Boundaries

Causoryn is a **local, LLM-free** MCP code-analysis server. Its automated security tests cover the following boundaries.

1. **Read-only source analysis (`ADR-008`):** Analyzers read project files. Persistent graph and wiki databases must resolve outside `allowRoots`. Automatic setup places exports outside the workspace. Explicit export destinations follow `output.allowedOutputDirs`, which can authorize a location inside a workspace.
2. **Explicit authorization & default deny:** Running the bare stdio server without CLI workspace flags defaults to `{"allowRoots":[]}` and fails closed with `WORKSPACE_NOT_AUTHORIZED`. Packaged CLI `--allow-cwd` rejects filesystem roots, `$HOME`, Causoryn's own data directory, and plugin cache directories.
3. **Path containment & symlink/TOCTOU defense:** Workspace reads and authorized data/output writes enforce realpath containment, reject symlink/junction escapes, and check against dangling-symlink overwrites (CWE-59).
4. **Read-only Git access:** Git operations use the explicit `cat-file` and `ls-tree` allowlist via `execFile` with `shell: false`.
5. **Local & LLM-free analysis (`ADR-002`):** The engine has no model or embedding clients and sends no source code to a model or telemetry service. The optional Rust sidecar’s cold `cargo build --locked` may fetch locked crates. A connected host controls its own model calls and data handling. [ADR-002](docs/en/adr/ADR-002-no-llm.md)
6. **Clean MCP `stdout` channel:** `stdout` emits only JSON-RPC 2.0 MCP frames; all diagnostic logs are written exclusively to `stderr`.
7. **Offline HTML exports:** Architecture and interactive HTML apply escaping and restrictive Content Security Policy (CSP), and use no external assets. The interactive view uses inline JavaScript. Optional annotations undergo schema and graph-reference validation. The caller is responsible for the accuracy of the prose. [Security audit](docs/en/security-pass.md)

## Supply-Chain & CI/CD Security

Causoryn's GitHub Actions pipeline and release process enforce layered supply-chain controls verified automatically by `tests/ci-workflow.test.ts`:

- **Workflow & dependency security (`.github/workflows/security.yml`):** Runs fail-closed `zizmor` static workflow auditing, PR `dependency-review-action` (blocking `high`+ advisories and copyleft SPDX licenses), `npm audit --audit-level=high`, fail-closed `--locked-mode` NuGet JSON auditing (`dotnet list ... package --vulnerable --include-transitive --format json`), `cargo audit --deny warnings` on the shipped `native/rust-worker/Cargo.lock` (`cargo-audit` installed at an exact version with `--locked`), and `govulncheck` on the Go worker (exact version, run on the `go.mod` toolchain with `GOTOOLCHAIN=local`). The Go worker declares the oldest still-supported Go release line in `native/go-worker/go.mod`.
- **5-language SAST (`.github/workflows/codeql.yml`):** Runs CodeQL v4 (`security-extended`) across `javascript-typescript`, `python`, `csharp`, `go`, and `actions`.
- **OpenSSF Scorecard (`.github/workflows/scorecard.yml`):** Runs `ossf/scorecard-action` (`publish_results: true`) with SARIF upload to GitHub Code Scanning.
- **3-job SLSA release pipeline (`.github/workflows/release.yml`):** Every job runs `step-security/harden-runner` (`egress-policy: audit`) first.
  - `verify-and-test` (`contents: read`): tag format, package version and `origin/main` ancestry checks, locked builds, lint, secret scan, public-export leak gate, and the full test suite.
  - `build-and-pack` (`contents: read`, no tests): clean checkout and hermetic build; `SHA256SUMS.txt` and the CycloneDX 1.5 SBOM (`scripts/generate-sbom.mjs`) are generated immediately after `npm pack`, and the tarball and SBOM SHA-256 digests are exported as job outputs (after checking that `SHA256SUMS.txt` is byte-for-byte the two expected records) before the packed tarball is smoke-tested, then re-checked after the smoke test.
  - `publish` (`environment: release`, `id-token: write`, `attestations: write`, `contents: write`): runs no build or test code; recomputes the downloaded digests and compares them with the `build-and-pack` job outputs (not only with the `SHA256SUMS.txt` shipped in the same artifact), rebuilds the expected two-record checksum list (tarball, then SBOM) from those outputs, requires the downloaded `SHA256SUMS.txt` to be byte-for-byte identical to it, and runs `sha256sum --strict -c` only on the locally rebuilt list (never on the downloaded file); then runs `actions/attest-build-provenance`, and publishes via tokenless npm OIDC Trusted Publishing (`npm publish --provenance --access public`; zero `NPM_TOKEN` secrets). GitHub Release assets are never overwritten: on a rerun an existing asset must have the same SHA-256, otherwise the job fails.
- **Locked, SHA-pinned CI & cooldown (`.github/workflows/ci.yml`, `.github/dependabot.yml`):** 100% 40-character SHA-pinned GitHub Actions, `persist-credentials: false`, zero `${{ ... }}` interpolation in `run:` steps, `npm ci --ignore-scripts`, `-p:RestoreLockedMode=true`, `cargo build --locked`, `scripts/export-public-tree.mjs --verify-temp --ref HEAD`, and a 7-day supply-chain Dependabot cooldown across 4 ecosystems (`npm`, `cargo`, `nuget`, `github-actions`). The merge gate runs on `ubuntu-latest`, `windows-latest` and `macos-26-intel`; the `main` branch ruleset requires the `Verify (ubuntu-latest)`, `Verify (windows-latest)` and `Verify (macos-26-intel)` checks. The nightly and manually dispatched runs add the Apple Silicon `macos-26` leg.
- **Host manifests:** plugin manifests start the launcher through the host's plugin-root variable (`${CLAUDE_PLUGIN_ROOT}`, `${ZCODE_PLUGIN_ROOT}`, Antigravity `${PLUGIN_ROOT}`) or, for Codex, which expands no variables, through an inline bootstrap (`node --input-type=module --eval …`, `env_vars: ["CODEX_HOME"]`, `env: {"NoDefaultCurrentDirectoryInExePath": "1"}` so `cmd.exe` and the server's child processes never search the current directory) that imports only `node:` built-ins, refuses a `node` binary inside the workspace and an empty or non-absolute `PATH` entry before the one that supplies `node`, and loads the launcher by its absolute real path in Codex's plugin cache, failing closed (exit `2`) when that path cannot be proven; never through a path relative to the analyzed project. The ZCode and Antigravity servers start in the plugin root (ZCode passes the project as the validated `--project-dir`), and the `npx` manifests pin npm's prefix to the plugin's data directory and pass `--ignore-scripts` (the published package has no dependencies and no install scripts). `tests/host-manifest-launch-safety.test.ts` checks every shipped manifest and pins the Codex bootstrap by SHA-256. Documented exceptions without a plugin-root `cwd`: the Claude Code manifest (no `cwd` field), the Codex manifest (runs in the session directory, `node` resolved from `PATH`; an empty or relative `PATH` entry before Node's directory can still select a project `node`, which then runs instead of the bootstrap, and a static manifest cannot name an absolute Node binary because Codex expands no variables and has no per-platform command; `causoryn setup` registers the absolute Node binary), and the MCP Registry `server.json` (no working-directory field). `server.json` passes `--ignore-scripts --prefix=~/` to `npx`, so npm treats the home directory as the project and the analyzed repository's `.npmrc` and a committed `node_modules/causoryn` do not decide what npm runs, and it sets `NoDefaultCurrentDirectoryInExePath=1` (`environmentVariables`), so on Windows `cmd.exe` does not search the current directory for `causoryn` or `node`. npm still puts `<cwd>/node_modules/.bin` (and every parent's) on `PATH` after the package's own bin directory, so the package's npm bin is a launcher without a shebang (`scripts/causoryn.cmd`, one file that POSIX `sh` and `cmd.exe` both read) that starts `scripts/causoryn.mjs` with the absolute Node npm runs (`npm_node_execpath`), never a `node` found on `PATH`. It passes Node no option except the `-e` of its POSIX branch, because the indexer's worker threads inherit Node's options (`tests/open-source-distribution.test.ts` indexes a project through the packed bin under the registry entry). Without npm (a global install) the launcher takes `node` from `PATH`: on POSIX the first `node` on `PATH`; on Windows the first `node.exe` that `%~$PATH:` finds, refusing (exit `2`) one in the current directory or below it, which an empty, `.` or other relative `PATH` entry (`sub`, `.\sub`, `node_modules\.bin`) selects (a prefix check on whole directory names; a relative entry that resolves outside the current directory is used as `PATH` says). On Windows the launcher never puts its arguments on a `cmd.exe` command line again (cmd-shim's shim is the level npm escapes them for): it echoes them unparsed (`REM` lines in `FOR` bodies, which `cmd.exe` does not act on) into two files in a new directory under `%LOCALAPPDATA%\causoryn\argv`, with the console switched to UTF-8 (`chcp 65001`, restored right after, so no best-fit conversion), and `scripts/lib/windows-argv.mjs` removes the files, splits the text as the C runtime does and starts the CLI. Trust assumption: whoever can write that directory between the two steps chooses the CLI's arguments, so the captures are not in `%TEMP%` (which can grant other accounts or groups Modify, for example a shared temporary directory at a drive root or a sandbox group's ACL entry) but under `%LOCALAPPDATA%`, which by default only the user, SYSTEM and administrators can write, and whoever can write it can already change the launcher in npm's cache there; the launcher refuses to start without an absolute `LOCALAPPDATA`. The code page belongs to the console, not the process: starts that share a console take a lock directory (`argv\lock`) for the switch, the captures and the restore, and the launcher refuses (exit `2`) when the code page is no longer UTF-8 after the captures, so a program outside Causoryn switching it at that moment gives a refusal, not wrong arguments. The lock holds its owner's token (`owner-<capture directory name>`) and the code page the owner found (`cp-<n>`); the owner releases it only while its token is still in it. A start waits up to 15 s for a lock; one unchanged for 15 s (its start was killed, or is that slow) is broken by moving it aside under a unique name, which only one waiting start can win (a lock taken by another start in between is put back), and a stale lock that cannot be moved (held open, for example by antivirus) counts as held; a `lock` that is a file or a link is refused at once, naming it. Every round of the wait checks its deadline, so a start never waits longer. Side effect: other programs in the same console see code page 65001 for those few milliseconds. A start killed inside that window leaves the console at 65001; the start that breaks its lock switches the console back to the recorded code page if the console is still at 65001 (a stale lock from another console, while this one was deliberately set to 65001, would switch this one too). Capture directories that a start left behind (node did not start or crashed, or removal failed) are removed by a later start once they are 10 minutes old and hold only capture files. `chcp.com` is run by absolute path with no `cmd.exe` of its own, so the user's `cmd.exe` AutoRun does not run. Every argument reaches the CLI exactly as the previous `#!/usr/bin/env node` bin passed it, including `&`, `|`, `<`, `>` and `^` outside quotes, `/?`, best-fit look-alikes of `"` such as U+FF02 `＂` and U+201C `“`, full-width operators and CJK text. Refused (exit `2`), never run: an argument with a `FOR` variable reference the two captures would expand (`%~`, `%#`, `%]`), and any start where the captures are missing or differ, the console code page cannot be read or switched (no console) or changed during the captures, a `lock` that is not a directory, or a lock that another start keeps (or that cannot be moved) for the whole 15 s wait. `tests/registry-npx-context.test.ts` runs the real npm against the measured hijacks — `node_modules/.bin/node` (`node.cmd` on Windows), a repository-root `node.cmd`, a current-directory `node.exe`/`node.cmd` for a global install, and a repository-root `causoryn.cmd` — and against these arguments, also in console code pages 437, 857, 1252 and 932 and with eight starts at once in one console, and shows that the previous `#!/usr/bin/env node` bin ran the hijacks and the launcher does not. Documented residuals: (1) on POSIX the Registry entry gives no protection against a hostile repository: npm starts the command through a bare `sh` looked up on that `PATH`, so the repository's `node_modules/.bin/sh` runs first (pinned in the same test); (2) the client resolves `npx` itself; (3) a global install started from PowerShell (`causoryn.ps1`) or Git Bash (`causoryn`) runs the launcher, a `.cmd` file, through `cmd.exe /c`, and those shells quote an argument only when it contains spaces, so in an argument without spaces `cmd.exe` acts on `&`, `|`, `<`, `>` and `^`, expands `%NAME%` and treats `＂` as text before the launcher starts (BatBadBut; measured with Windows PowerShell 5.1 and Git Bash and pinned in the same test; the previous bin's `.ps1` and `sh` shims started `node.exe` directly) — nothing in the launcher can see or undo that; (4) the bin has no shebang, so a program that starts it without a shell gets `Exec format error` unless its exec falls back to `sh` on `ENOEXEC`: glibc's `execvp` does (Node on Linux works), Python's `subprocess` does not (measured, `OSError` 8), and per the independent review neither do Node on macOS (libuv uses `posix_spawn` there: `spawn Unknown system error -8`) and Rust and Go clients. `causoryn setup` avoids all of them by registering the absolute Node binary and the absolute `scripts/causoryn.mjs`: no shell, no `PATH` lookup, no launcher.

## Out of Scope

The following are outside Causoryn's security boundary:

- Vulnerabilities in third-party host applications (Antigravity, Claude Code, Codex, ZCode) or their LLM models
- Model hallucinations or tool-selection decisions made by the host LLM outside Causoryn's structured MCP output
- Attacks requiring an adversary who already possesses arbitrary local code execution as the user before Causoryn starts
- Denial-of-service caused solely by intentionally passing arbitrarily huge inputs after raising configured safety limits
- Absent optional language toolchains (`dotnet`, `python`, `go`, `cargo`), which intentionally degrade to L0/L1 file-level provenance
